# Historical model M1 — structural extension

Gate: **SAFE — M1 HISTORICAL STRUCTURAL EXTENSION IMPLEMENTED — READY FOR M2**

> The model can now carry history; it has not been told any.

M1 implements the structures M0 specified (`docs/PHASE-M0-HISTORICAL-SCHEMA.md`, `c0a4b4b`) in the
real model contract and validator.

**No historical fact, document date, transition, claim or disposition was written.** No row of
`data/model/` changed, and no generated file, application file, evidence, provenance or discovery
record changed. D2 is undecided, D5 is not applied, and the name `RELATED_UNSPECIFIED` stays
provisional.

## 1. What was implemented

| File | Change |
|---|---|
| `docs/schema/historical-m1-contract.json` | **new.** The contract extension in force: the two enumerations, the transition kind, the TimeWindow type, five optional fields, `IdentityTransition.at` loosened, the historical reconciliation fields and the rules allowed before D5 |
| `tools/model_schema.py` | merges the extension into the contract on load; enforces the TemporalBound precision rule; checks interval axes and order; validates TimeWindows and dispositions; adds the row-level historical rules (`check_history`); `check_row` takes an optional provenance lookup |
| `tools/test-historical-m1.py` | **new.** 24 structural checks |
| this document | **new** |

**Where the extension lives.** The Phase 3.4 contract (`docs/phase34-model.json`) is generated by
`tools/build-phase34-model.py`. It is a protected group in `data/model/baseline.json`
(`phase34_model`), held by `tools/phase4-baseline.py --check`. Editing it in place would mean
rewriting the model's baseline file and Phase 3.4's builder.

M1 therefore keeps it untouched and adds a **versioned extension file**, merged by the existing loader
(`tools/model_schema.py`). It is one vocabulary, one validator and one contract as loaded; not a
parallel model.

This is a choice of where the contract is stored, **not a change to the M0 schema**: every
enumeration, type, field and rule is exactly as M0 specified. The model manifest
(`data/model/manifest.json`) still names `docs/phase34-model.json` as its contract. Changing that
would rewrite a model file, and no model row uses an M1 field yet. The manifest can name the
extension when M2 or M3 first writes one.

## 2. The exact model changes

| Structure | Added | Values and semantics |
|---|---|---|
| enum **StatementMode** | new | `EXPLICIT` (stated in words), `IMPLIED` (from the document's framing only) |
| enum **CandidateDisposition** | new | `SELECTED`, `CONSISTENT`, `CONTRADICTS`, `REJECTED`, `NOT_ASSESSED` |
| enum **TransitionKind** | + `RELATED_UNSPECIFIED` | the six existing kinds unchanged |
| value type **TimeWindow** | new | {earliest, latest}, each a TemporalBound; no OPEN or NOT_APPLICABLE; one axis; earliest ≤ latest |
| **Observation.claimed_validity** | optional, Validity | the span a source says a state holds |
| **Observation.claimed_window** | optional, TimeWindow | the window a source says an event happened in |
| **Observation.statement_mode** | optional, StatementMode | required when either claim field is present; refused without one |
| **IdentityTransition.occurred** | optional, TimeWindow | when the transition happened, as tightly as known |
| **IdentityTransition.at** | required → optional | a transition has **exactly one** of `at` and `occurred` |
| **Reconciliation.dispositions** | optional, `{candidate id: {disposition, reason}}` | beside the unchanged `candidates` list; a candidate without an entry is NOT_ASSESSED |

**The date primitive is unchanged.** The existing TemporalBound carries kind, axis (CALENDAR,
VINTAGE), value, precision and basis. TimeWindow and the existing Validity are both built from it.

**Four times stay apart.** The window is when an event happened. It is never:

- the document's date (`asserted_at`);
- its retrieval (Placement);
- its reconciliation (`decided_at`).

**Not added:** the evaluator (`holds`, `evaluate`, `state_at`, `changes`) and its statuses (ESTABLISHED,
CONTESTED, UNDETERMINED, NOT_ESTABLISHED). M1 has no historical reasoning, and no placeholder was
needed.

## 4. Validation rules added

These are runtime checks in `tools/model_schema.py`, M0's invariants as numbered there:

| Rule | M0 | Check |
|---|---|---|
| a dated bound's value matches its precision: DAY, MONTH, YEAR, DECADE on CALENDAR; a year with precision VINTAGE on VINTAGE | S2 | `check_bound` |
| the two dated bounds of one interval share an axis; no conversion | S3 | `check_order` |
| the lower bound is not after the upper, at the coarser precision | S4 | `check_order` (Validity and TimeWindow) |
| OPEN only as valid_to, never in a window; NOT_APPLICABLE not in a window | S5 | `check_validity`, `check_window` |
| a claim is about a state or an event, not both; `statement_mode` is required with a claim and refused without one | S7 | `check_history` |
| a temporal claim cites an artifact, or a provenance with a quote | S18 | `check_history` (with the optional provenance lookup) |
| a transition has exactly one of `at` and `occurred` | O4 | `check_history` |
| RENAMED relates a subject to itself; SUCCEEDED_BY relates two subjects of one type | S8 | `check_history` |
| RELATED_UNSPECIFIED and POSSIBLY_SAME are UNRESOLVED: they establish nothing | S9 | `check_history` |
| a disposition is a known value; REJECTED needs a reason | S14 | `check_dispositions` |
| dispositions only for candidates; one SELECTED, matching `selected` | S14 | `check_history` |
| no selection while CONFLICT_OPEN or DEFERRED | S15 | `check_history` |
| a historical field's reconciliation uses only ONLY_CANDIDATE, UNANIMOUS or MANUAL_DECISION until D5 | S16 | `check_history` |

**Existing rules still apply:** S1 (a dated bound has value, axis and basis) and OPEN only as an end.

**Duplicate dispositions** cannot occur in the structure: it is a mapping keyed by candidate.

**Not runtime checks:**

- **For the evaluator (M3/M4):** S10, S21, S24, S26.
- **For M2 and M3 data review:** S6 (a bound taken from an ArtifactDate is IMPLIED), S11–S13 and S17.
  They need ArtifactDates and reconciled records, and none exist yet.

## 6. Why no history was added

M1 is structure. Adding a fact needs, per the design (§12):

- **claims** extracted from documents (with M2's document dates);
- **a reconciliation** of those claims;
- **a recorded decision** for every fact, until D5 exists.

None of these is M1's to make. Writing even one example into `data/model/` would turn a schema test
into an undocumented decision. So M1's examples live **only in test code**, as rows built in memory.

**D2 and D5 stay unresolved:**

- **D2 (rename versus succession, for Echo):** the schema now holds either. RENAMED with from == to,
  or SUCCEEDED_BY between two Wines. Choosing is a domain decision about a real wine, and M1 writes no
  real wine's history.
- **D5 (conflict policy):** not applied. M1 *enforces its absence*: no historical reconciliation may
  use MOST_RECENT_DOCUMENT or SOURCE_PRIORITY, and nothing selects automatically.

## 7. The provisional `RELATED_UNSPECIFIED`

It is added under the design's name, as M0 recorded. The brief's `RELATED_NOT_ESTABLISHED` names the
same meaning. The contract was not updated to that name, so M1 does not use it.

**Its rules:** it is always UNRESOLVED, establishes no identity, and is checked like any kind.

**Renaming it (decision O3)** is a one-line change in `historical-m1-contract.json` while no row uses
it. **After M3 writes one, renaming would be a migration.**

## 8. Tests

**`tools/test-historical-m1.py`**, 24 checks.

The brief's 20 cases, each on rows built in memory:

1. an observation with no historical fields;
2. explicit and
3. implied claimed validity;
4. a claimed event window, which needs a mode and a source;
5. a calendar window, with precision enforced;
6. a vintage window, with no axis conversion;
7. an unknown or open lower bound: OPEN refused as a start;
8. an open upper bound for a state only, not in a window;
9. an unknown date: UNKNOWN with a value refused;
10. reversed bounds refused; the same year at two precisions accepted;
11. a transition with `at`;
12. a transition with `occurred`;
13. a transition with neither fails;
14. a transition with both fails;
15. `RELATED_UNSPECIFIED` UNRESOLVED only, plus rename ≠ succession and the existing kinds accepted;
16. each disposition, the D5 guard and no selection while CONFLICT_OPEN;
17. REJECTED without a reason fails;
18. a disposition for a non-candidate fails;
19. one observation with different dispositions in two reconciliations; no disposition field on
    Observation;
20. every legacy row valid with the historical fields absent (333,022).

Four more checks:

- **nothing populated:** every structure in section 5 is empty;
- **the extension makes no current fact historical:** 3,917 records, still UNKNOWN to OPEN;
- **the model, generated data and protected groups are unchanged:** the 12,959 candidate lists
  identical;
- **the Phase 3.4 contract is untouched and extended by merge;** no evaluator in M1.

**The checks can fail.** Run against the pre-M1 `tools/model_schema.py` (`c0a4b4b`), the 18 checks of
the new structures fail. The 6 that pass there pass by design: they are compatibility and
no-population checks, plus an observation without the new fields and a transition dated with `at`.

**The M0 validator** (`docs/schema/check_historical_m1_proposal.py`) still passes: 48 checks.

## 9. Regression

| | Suites | Checks |
|---|---:|---:|
| existing baseline | 27 | 740 |
| with M1 | **28** | **764** (+24) |

All pass with `tools/run-tests.py`. No existing test was changed.

**One intermittent failure, recorded rather than dismissed.**

- **What happened:** in the first full run at 2 workers, `tools/test-phase65.py` failed one check.
  The runner's output naming the check was not kept.
- **It did not reproduce:**
  - test-phase65 passed alone;
  - it passed three times alongside test-phase63 and test-phase4;
  - the next full run passed (28 suites, 764 checks).
- **M1 cannot have caused it:**
  - test-phase65 and `build-app-data.py` never call the validator;
  - `model_reader` uses only `model_schema.hid`, which M1 did not change.
- **The likely cause:** this is the browser-timing class Phase 6.6B identified. Fixed sleeps remain in
  some checks, and condition waits were deferred as O6.
- **Follow-up:** replace those sleeps (O6), outside M1.

| | M1 | M2 |
